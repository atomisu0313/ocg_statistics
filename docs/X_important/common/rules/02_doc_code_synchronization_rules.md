# ルール: コード修正時における docs ドキュメント見直し・同期原則

本リポジトリ（`ocg_statistics`）において、アプリケーションコード、インフラ定義、DB マイグレーション、スクリプト等を修正・追加した際は、**必ず対応する [docs/](../../..) 配下のドキュメントも見直し、コードと設計資料の同期を維持すること**を義務付けます。

---

## 1. 背景と目的

開発が進むにつれて「コードは更新されたがドキュメントは古いまま放置される（Doc-Code Drift）」状態が発生すると、以下の弊害が生じます：

1. **新規参入者や後続開発の混乱**:
   - 設計図やクラス図を信じて実装したら実際の実装と異なり、手戻りやバグの原因になる。
2. **アーキテクチャ規律の崩壊**:
   - 当初のレイヤー責務や命名規則が形骸化し、属人的なスパゲッティコードが蓄積される。
3. **障害対応・調査の遅延**:
   - トラブルシューティング時に古い手順書や誤った構成図を参照し、復旧が大幅に遅れる。

コードとドキュメントは**「不可分な 1 つの成果物」**であり、コードの変更とドキュメントの更新は同一の作業・PR で完結させなければなりません。

---

## 3. 遵守ルール一覧

1. **コード変更とドキュメント修正を同一 PR / コミットに含めること**
   - 「ドキュメントは後で別 PR で書く」は原則禁止とする。コード変更と同時に docs の差分も含めて提出する。
2. **Mermaid 図・クラス図・対応表の乖離を放置しないこと**
   - テーブルやフィールド、クラス間のリレーションが変わった場合、Mermaid 記法の図や Markdown テーブルを即座に最新化する。
3. **手順書に書かれたパス・コマンドの正確性を保証すること**
   - スクリプト名や実行ディレクトリを変更した場合、ドキュメント内の `cd ...` コマンドや相対パス指定を必ず修正・実機テストする。
4. **仕様変更時は「なぜそうしたのか」の設計方針を追記すること**
   - 単にコード差分に合わせるだけでなく、アーキテクチャ上の判断理由（例: DTO 採用理由など）を関連 docs に明記する。

## 4. 運用・記述例

### ⭕ 正しい運用例
```text
【PR タイトル】feat: カード画像保存テーブルの追加とパイプライン実装
【変更ファイル】
- database/migrate/db/migrations/000003_create_card_images... (DB定義)
- code/cardApiCall/infoInsert/repository/card_image.go       (実装)
- code/cardApiCall/infoInsert/dto/cardrecord/carddto.go      (DTO定義)
- docs/01_data_prepare/card_class_diagram.md                 (クラス図 & 対応表を更新) ★
- docs/03_card_image/01_card_image_architecture.md          (画像設計書を更新) ★
```
> ※コードの変更と連動して、関連する `docs/` が漏れなく同一 PR で更新されている。

### ❌ 違反例（アンチパターン）
```text
❌ 違反 1: 「コードだけマージして docs は放置」
→ テーブルを追加したのに card_class_diagram.md が更新されず、ドキュメントが嘘をつく状態になる。

❌ 違反 2: 「スクリプトのディレクトリを変えたのに手順書を直さない」
→ README に書かれたコマンドを実行するとパス不正でエラーになり、運用が混乱する。
```

## 5. 実装チェックリスト

コード修正を完了する前に、以下の項目をすべて確認してください：

- [ ] 今回修正したコードに対応する [docs/](../../..) 配下のドキュメントを特定したか？
- [ ] クラス図・シーケンス図・フロー図（Mermaid）は最新の実装と一致しているか？
- [ ] テーブル名・カラム名・DTO 名がドキュメント内の対応表と整合しているか？
- [ ] 手順書に記載されているコマンドや実行パスが正常に動作するか確認したか？
- [ ] コードの変更とドキュメントの更新が同一の変更コミットに含まれているか？
